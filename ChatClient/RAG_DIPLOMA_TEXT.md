# RAG в проекте `ChatClient` (текст для диплома)

Для прикладного проекта `ChatClient` задача Retrieval-Augmented Generation (RAG) приобретает предметный смысл и выступает не как абстрактная концепция, а как практический архитектурный механизм. Под RAG понимается подход, при котором генерация ответа языковой моделью дополняется этапом поиска релевантной информации во внешнем хранилище: система сначала извлекает подходящие данные (retriever), а затем использует их при формировании результата (generator). В отличие от сценариев, где модель опирается только на внутренние параметры, такой подход делает вывод фактически привязанным к данным предметной области, поскольку в процессе обработки запроса используются актуальные контексты, найденные по семантической близости векторных представлений (embeddings). В контексте `ChatClient` это особенно важно, поскольку системе требуется не просто “ответить текстом”, а корректно интерпретировать намерение пользователя, определить, что сообщение относится к заказу, нормализовать формулировку, преобразовать ее в структурированный формат и согласовать позиции с реальным каталогом продуктов. Следовательно, RAG здесь выполняет функцию grounding (привязки) выходов LLM к фактам, хранящимся во внешних данных, а извлечение релевантных сущностей используется не как вспомогательное пояснение, а как источник истины при формировании итогового JSON-представления заказа.

В реализации `ChatClient` этап retrieval обеспечивается связкой “embeddings + векторное хранилище”. Эмбеддинги пользовательских формулировок и/или текстов продуктов формируются с использованием локальной модели через `Ollama`, а именно в конфигурации сервиса внедряется генератор эмбеддингов на базе `mxbai-embed-large` (`AddEmbeddingGenerator` с `OllamaApiClient("http://localhost:11434", "mxbai-embed-large")`). Семантический индекс формируется в базе данных PostgreSQL с расширением `pgvector`. Для хранения векторов используется модель `Chunk`, где поле `Embedding1024` соответствует типу `vector(1024)`, а также дополнительно хранится доменная информация `ProductInfo`, связанная с продуктом. Важным следствием такой модели является то, что retrieval выполняется по смыслу: система сравнивает вектор запроса с векторами сохраненных фрагментов (chunks) и извлекает те продукты, которые семантически ближе к описанию пользователя, чем остальные.

На этапе runtime retrieval реализован в инструменте `ProductTools.GetProductsByDescription`. Сначала метод получает текстовое описание из пользовательского запроса, превращает его в embedding через `EmbeddingService`, затем формирует вектор `Vector(embedding)` и выполняет векторный поиск по таблице `Chunks`. Условие релевантности задается через косинусное расстояние: используется фильтрация по порогу (в проекте — `CosineDistance(vector) < 0.4`) и сортировка по возрастанию дистанции (`OrderBy(... CosineDistance(vector))`), после чего возвращается список `ProductInfo` для наиболее релевантных продуктов. Такой подход согласуется с общими принципами RAG: семантическая близость используется для отбора контекстов, которые затем будут влиять на генерацию. При этом выбранный “юнит” retrieval — не произвольные предложения, а структурированные карточки продуктов, что делает pipeline более управляемым и совместимым с бизнес-ограничениями.

Этап generator в данном проекте реализуется через агента `OrdeCreaterAgent`, построенного на Microsoft Agent Framework. Хотя генерация выполняется языковой моделью, ключевое отличие от “чистого” генеративного режима заключается в том, что агент получает доступ к доменным инструментам, которые реализуют retrieval и проверку корректности данных. Внутри `OrdeCreaterAgent` объявлены функции tool calling: `get_products_by_description`, `get_product_by_id` и `validate_product_ingredients_quantities`. Когда агент интерпретирует нормализованный текст заказа и обнаруживает неопределенность в том, какие именно продукты соответствуют указанным пользователем формулировкам, он инициирует вызов `get_products_by_description`. Результатом этого вызова является набор релевантных продуктов, найденных retrieval-слоем (векторный поиск в `pgvector`). Затем агент использует полученные кандидаты для принятия решения и формирования JSON-структуры заказа. Если пользовательские указания требуют уточнения состава, агент вызывает инструмент `get_product_by_id` и дополнительно выполняет валидацию ингредиентов через `validate_product_ingredients_quantities`, что усиливает grounding: LLM не только сопоставляет намерение с каталогом, но и соблюдает количественные ограничения, формируя `customIngredients[]` на основе фактических правил продукта.

Таким образом, RAG в `ChatClient` является tool-augmented вариантом архитектуры. Retrieval не обязательно передается в виде “сырого текста документов” прямо в prompt; вместо этого retrieved-кандидаты возвращаются как результаты вызовов функций, которые агент затем использует при reasoning и построении структурированного выхода. Для прикладной задачи это особенно важно, поскольку конечный результат должен соответствовать заранее заданной JSON-схеме. В `OrderTextNormalizerExecutor` и `OrderParserExecutor` принуждение к структурированному формату реализовано через `ChatResponseFormat.ForJsonSchema<...>`, что в совокупности с retrieval-layer снижает вероятность несоответствий и облегчает последующую интеграцию с другими сервисами.

Отдельно следует подчеркнуть роль orchestration. Microsoft Agent Framework в `ChatClient` отвечает за контроль порядка шагов и условные переходы в workflow: нормализация и классификация текста выполняются до парсинга заказа, а ветвление по результату классификации позволяет обрабатывать нецелевые сообщения. Такая оркестрация дополняет RAG-инференс, поскольку retrieval активируется только в сценариях, где оно имеет смысл (когда сообщение действительно похоже на заказ). В результате pipeline становится не просто набором технических вызовов, а управляемым бизнес-процессом, который уменьшает количество бессмысленных retrieval-операций и повышает устойчивость системы.

В качестве итогового вывода можно утверждать, что RAG в `ChatClient` используется как инженерно обоснованный способ связать генеративные возможности LLM с фактическими данными предметной области. С точки зрения архитектуры система использует классическую идею retrieval (embeddings, векторный поиск по `pgvector`, пороговая и ранжирующая логика) и применяет ее в генеративной задаче структурирования заказа (агентное reasoning с tool calling и структурированным выводом). Для дипломной работы это важно тем, что подход демонстрирует практическую применимость RAG не только в текстовых ответах, но и в задачах “семантического сопоставления сущностей” и “валидируемой генерации” в бизнес-ориентированных приложениях.

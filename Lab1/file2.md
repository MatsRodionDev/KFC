Для обеспечения надежности и поддерживаемости кода в проекте KFC (каталог/заказы/оплата/чат/гео) устанавливаются следующие стандарты:
Код: использование ESLint для frontend (React + TypeScript) и статических анализаторов/правил форматирования для backend (.NET). Обязательная типизация в TypeScript и строгая обработка null/nullable в C#.
Архитектура: соблюдение разделения слоев `Domain / Application / Infrastructure` в .NET и разделение UI-логики/данных в React. Вынесение сетевых/фоновых операций (запросы, обработка событий, webhooks) в отдельные сервисы и воркеры, чтобы не блокировать основной поток обработки запросов и UI.
Надежность интеграций: для событий и webhooks обеспечивается идемпотентность обработчиков, ретраи с backoff и воспроизводимая обработка ошибок (логирование, корреляционные идентификаторы).
Документация: актуальная документация по API/контрактам событий (что и как публикуется/потребляется), инструкции по локальному запуску сервисов и схема деплоя на стенд.

| Уровень | Критерии завершенности (Definition of Done) |
|---|---|
| Задача (Task) | Изменения реализованы в соответствующем сервисе. Билд проходит (frontend: `lint`/`build`, backend: `build`). Локальные smoke-проверки сценариев выполнены. Pull Request создан, конфликтов слияния нет. |
| User Story | Все дочерние задачи завершены. Интеграционные сценарии для Story воспроизводимы на стенде (или через локальный docker/тестовые окружения). Критические дефекты устранены. |
| Спринт (Sprint) | Все User Stories интегрированы. Регрессионное тестирование ключевых потоков (каталог -> заказ -> оплата -> обновления статусов -> чат) пройдено. Известные критические дефекты устранены или закрыты по плану исправлений. |
| Релиз (Release) | Функциональность согласована с требованиями. Деплой выполнен в целевое окружение. Смоук-тесты end-to-end для основных контуров пройдены (каталог, создание заказа, обработка webhook, обновления по SignalR, корректность отображения в SPA). Выполнены базовые нагрузочные/устойчивостные проверки (минимальные KPI по задержкам). |

| Категория | Показатель | Целевое значение | Метод измерения |
|---|---|---|---|
| Каталог (Catalog) | Консистентность выдачи цен/наличия | >= 99% успешных ответов в E2E-сценариях | Интеграционные тесты на тестовой БД + сверка данных с ожидаемыми значениями |
| Заказ (Order) | Успешность создания заказа и публикации событий | >= 99% операций | E2E: создание заказа + проверка факта публикации событий/сохранения состояния |
| Оплата (Payment) | Успешность завершения оплаты через webhook и корректная смена статуса заказа | >= 99% платежей в тестовом контуре | Пакетная симуляция webhook Stripe + проверка конечного статуса заказа |
| Чат (ChatClient) | Время обработки сообщения заказа (end-to-end) | p95 <= 2 сек | Логирование/трекинг по корреляционному id + замер времени до обновления заказа |
| Обновления статусов (SignalR) | Задержка доставки обновлений клиентам | p95 <= 0.5 сек | Нагрузочный сценарий с тестовыми клиентами SignalR (измерение времени “от события до отображения”) |
| Надежность/доступность | Доступность ключевых API/хабов | >= 99.9% на период теста | Наблюдение (мониторинг) + длительное нагрузочное/устойчивостное тестирование |

Используется при проверке каждого Pull Request перед слиянием с основной веткой:
– Архитектура решения не нарушена (контракты/контур событий не “ломаются” без миграций и версии контрактов).
– Новая логика покрыта соответствующими тестами (unit для домена, интеграционные/контрактные для границ).
– Код соответствует принятому стайл-гайду (линтеры не выдают критичных ошибок) и проходит сборку.

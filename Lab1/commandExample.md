6. КОМАНДА ПРОЕКТА

   6.1 Структура команды

Роль	Основные обязанности
Project Manager / ML Engineer	Управление проектами, коммуникация со спонсором. Проектирование и обучение нейросетей (YOLO, LSTM).
Python Core Developer / DevOps	Разработка логического ядра. Сборка EXE-файла и настройка окружения.
GUI Developer / QA Engineer	Разработка интерфейса на Tkinter. Функциональное тестирование, написание документации.

Организационная структура:
•	Уровень 1: Спонсор проекта (Мисник А. Е.).
•	Уровень 2: Менеджер проекта (Хмельков И. В.).
•	Уровень 3: Исполнители (ML Engineer, Python Dev, GUI Dev).

Общая трудоемкость проекта: ~325 человеко-часов.

Общая потребность в человеко-месяцах: 2.03 человеко-месяца.
Средний FTE на проект: 0.29.

Общее покрытие компетенций: Команда полностью укомплектована необходимыми специалистами. По всем критическим технологиям (Python, ML, Win32 API, GUI на Tkinter) текущий уровень владения навыками у основных исполнителей соответствует заявленным требованиям (уровень 4 — Эксперт) или превышает их. Дефицита квалификации для старта проекта не выявлено.
Потенциал взаимозаменяемости: В команде наблюдается высокий уровень перекрестных компетенций, снижающий риски простоя разработки:
•	Python-разработка (General): наиболее устойчивый сегмент. Сразу две роли (PM / ML Lead и Python / DevOps) владеют языком на экспертном уровне (4), а GUI / QA — на уверенном (3). Это позволяет всей команде эффективно взаимодействовать, писать и ревьюить основной код системы.
•	Машинное обучение (PyTorch, Ultralytics): Основной эксперт — PM / ML Lead (уровень 4), однако он надежно подстрахован специалистом Python / DevOps (уровень 3). Это позволяет совместно решать задачи интеграции и дообучения моделей.
•	Разработка интерфейсов (GUI) и Тестирование: Профильный специалист GUI / QA владеет этими навыками на уровне 4. При необходимости PM / ML Lead способен подменить его в разработке интерфейсов на Tkinter (уровень 3), а Python / DevOps — помочь с тестированием ПО (уровень 3).
•	DevOps и сборка (PyInstaller, Env): Процесс сборки и настройки среды не зависит от одного человека. Экспертиза Python / DevOps (4) подкреплена уверенными знаниями PM / ML Lead (3).

Идентификация рисков и незаменимых сотрудников: Выявлены «узкие места», требующие особого внимания при управлении ресурсами:
•	Критический риск (Win32 API / MSS): Низкоуровневым взаимодействием с ОС (эмуляция мыши, быстрый захват экрана) на экспертном уровне (4) владеет только Python / DevOps. У остальных членов команды компетенции в этой области минимальны (1–2), что делает данного специалиста незаменимым на этапе интеграции алгоритмов с ОС.
•	Управленческий риск (Управление проектами): В команде отсутствует управленец экспертного уровня (4). Высший балл компетенции (3) находится у PM / ML Lead. Частичное делегирование возможно на GUI / QA (уровень 2), однако при длительном отсутствии лида может снизиться качество контроля сроков.
Вывод: Команда обладает отличным запасом прочности для реализации ML-моделей, базовой логики и графического интерфейса благодаря сильной общей базе Python. Для минимизации рисков по специфичной интеграции с ОС рекомендуется проводить регулярные сессии обмена знаниями (code review, документация механизмов Win32 API) между специалистом Python / DevOps и PM / ML Lead.
